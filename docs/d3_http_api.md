# D3 历史复盘数据接口

## 这份文档解决什么问题

D3 用来按“交易日期 + 股票代码”读取一份历史复盘数据。它适合做分时回放、成交明细查看、盘口变化分析和离线研究。

本文面向第一次调用接口的用户，说明：

- 如何在本地服务启动后发出第一条请求；
- `date`、`id` 两个入参应该怎么填写；
- 返回 JSON 的整体结构和每个字段的含义；
- `tick` 与 `deal` 两类数组为什么不是固定列；
- 百分比、价格、数量、状态码和空值应该怎样处理；
- 如何判断权限、日期、代码或数据解析是否出现问题。

本文只描述当前用户界面中可见的 D3 接口。未出现在本文中的隐藏或内部接口，不属于用户侧使用范围，也不建议自行拼接调用。

---

## 1. 零基础快速开始

### 1.1 先启动本地服务

在客户端中完成登录并确认账号具有 D3 使用权限，然后在端口框中保留默认值 `8080`，点击“启动”。看到服务处于运行状态后，才能访问下面的地址。

默认 D3 地址：

```text
http://127.0.0.1:8080
```

如果你在客户端把端口改成了其他数字，需要把示例中的 `8080` 替换成实际端口。D3 请求必须发给本机服务，不需要在代码中填写外部服务器地址、账号密码或内部认证字段。

### 1.2 用浏览器页面完成第一次请求

1. 打开本地接口页面，在左侧选择 `d3`。
2. 选择“历史复盘数据”。
3. 填写日期，例如 `20250508`；填写股票代码，例如 `SZ002306`。
4. 点击“发送”，确认右侧能看到 JSON。
5. 页面中的“复制 curl”可以生成一条可直接迁移到命令行的请求。

建议第一次先使用页面成功生成的请求。确认返回正常后，再把日期和股票代码替换成自己的参数。

### 1.3 curl 调用

Windows PowerShell、命令提示符或 macOS/Linux 终端都可以使用下面的形式：

```bash
curl -G "http://127.0.0.1:8080/d3/history" \
  --data-urlencode "date=20250508" \
  --data-urlencode "id=SZ002306"
```

Windows PowerShell 如果系统把 `curl` 映射成其他命令，可以明确使用 `curl.exe`：

```powershell
curl.exe -G "http://127.0.0.1:8080/d3/history" `
  --data-urlencode "date=20250508" `
  --data-urlencode "id=SZ002306"
```

### 1.4 Python 调用

```python
import requests

url = "http://127.0.0.1:8080/d3/history"
params = {
    "date": "20250508",
    "id": "SZ002306",
}

response = requests.get(url, params=params, timeout=30)
response.raise_for_status()
result = response.json()

print("数据日期:", result.get("date"))
print("分段数量:", len(result.get("segments", [])))
```

如果返回 `403`，先回到客户端检查登录、权限和服务启动状态；不要把账号密码拼到 D3 URL 中。

## 2. 接口定义

| 项目 | 内容 |
|---|---|
| 接口名称 | 历史复盘数据 |
| 方法 | `GET` |
| 路径 | `/d3/history` |
| 完整地址 | `http://127.0.0.1:{端口}/d3/history` |
| 返回格式 | `application/json` |
| 当前可见接口数量 | 1 个 |

### 2.1 请求参数

| 参数 | 类型 | 必填 | 示例 | 说明 |
|---|---|:---:|---|---|
| `date` | 字符串 | 是 | `20250508` | 交易日期，格式为 `YYYYMMDD`，必须是 8 位数字。 |
| `id` | 字符串 | 是 | `SZ002306` | 股票代码，保留市场前缀和 6 位数字，不要填写股票名称。 |

### 2.2 参数填写规则

#### `date`

- 使用 8 位日期：`20250508` 表示 2025 年 5 月 8 日。
- 不要写成 `2025-05-08`、`2025/05/08` 或 Unix 时间戳。
- 日期最好选择交易日。周末、节假日或尚未产生数据的日期，可能返回空分段、空数组或业务错误。
- 日期是请求条件，不是返回数组中每一条记录的时间。每一条记录的时间见 `time` 字段。

#### `id`

- 使用市场前缀 + 6 位股票代码，例如 `SZ002306`、`SH600000`。
- 必须保留前导零，例如 `SZ000001` 不能写成 `SZ1`。
- 页面示例使用大写前缀；服务端会兼容处理大小写，但建议始终发送大写，便于日志、缓存和数据对账。
- 不要把股票名称、简称或带空格的描述放进 `id`。

## 3. 返回 JSON 总体结构

成功时，返回对象通常包含以下字段：

```json
{
  "date": 20260805,
  "is_paid": true,
  "segments": [
    {
      "index": 1,
      "date": 20260805,
      "type": "tick",
      "data": []
    },
    {
      "index": 4,
      "date": 20260805,
      "type": "deal",
      "data": []
    }
  ]
}
```

完整数据通常很大，上面的数组只展示结构，不代表实际只有两条记录。返回的 `segments` 数量以实际响应为准；不同日期和股票可能包含不同数量的分段。

### 3.1 顶层字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `date` | 整数 | 返回包标记的数据日期，形如 `YYYYMMDD`。 |
| `is_paid` | 布尔值 | 返回包中的可用性/权限标记。它不是涨跌状态、成交状态，也不是某一笔成交的买卖方向。为 `false` 时，应结合 HTTP 状态、`segments` 和实际数据一起判断。 |
| `segments` | 数组 | 数据分段列表。每个分段有自己的 `index`、`date`、`type` 和 `data`。 |

### 3.2 分段字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `index` | 整数 | 分段序号。当前已确认第 1 段是 `tick`，第 4 段是 `deal`。 |
| `date` | 整数 | 该分段的数据日期。通常与顶层 `date` 相同。 |
| `type` | 字符串 | 当前可能看到 `tick`、`deal`、`segment_2`、`segment_3` 或 `segment_5`。 |
| `data` | 数组或对象 | `tick`、`deal` 为记录数组；尚未展开字段的分段为对象，例如 `{"raw_len":120805}`。 |

### 3.3 当前各分段的可用程度

| `type` | `data` 形态 | 当前能直接使用的内容 |
|---|---|---|
| `tick` | 数组 | 分时行情、累计量、盘口摘要、盘口变动。 |
| `deal` | 数组 | 成交明细。每条记录可能只有部分字段。 |
| `segment_2` | `{"raw_len":整数}` | 只有解压后的字节长度，不要把它当作记录数。 |
| `segment_3` | `{"raw_len":整数}` | 只有解压后的字节长度，不要自行猜测字段。 |
| `segment_5` | `{"raw_len":整数}` | 只有解压后的字节长度，不要自行猜测字段。 |

`raw_len` 是解压后数据的字节数，不是行情条数、成交笔数或股票数量。尚未展开的分段在用户侧文档中不提供虚构的字段解释。

## 4. 先理解一个关键规则：记录是“稀疏的”

D3 的二进制记录采用“本条只传发生变化的字段”的方式。也就是说，不要假设数组中的每个对象都有完全相同的键。

### 4.1 `tick` 的规则：缺少字段时沿用上一条状态

例如，前一条记录有：

```json
{
  "time": 91500,
  "price": 1.71,
  "volume": 45100
}
```

后一条记录可能只改变成交量：

```json
{
  "time": 91509,
  "price": 1.71,
  "volume": 92100
}
```

后一条原始记录即使没有再次携带价格，解析后的结果也会保留上一条价格。应用层读取 `tick` 时，应按返回数组顺序处理；不要因为某个原始字段没有再次出现，就把它当成 0。

### 4.2 `deal` 的规则：只保留本条实际出现的字段

成交明细中，某条记录可能是：

```json
{
  "seq": 0,
  "time": 91500,
  "price": 1.75,
  "volume": 96800,
  "status": 4
}
```

下一条可能是：

```json
{
  "seq": 0,
  "time": 91509,
  "price": 1.76,
  "volume": 97000
}
```

再下一条也可能只有：

```json
{
  "seq": 0,
  "time": 91527,
  "volume": 96800
}
```

这里缺少 `price` 或 `status` 表示该条记录没有携带这个字段，不表示价格为 0，也不表示解析失败。对 `deal` 做表格化处理时，应使用“字段不存在”而不是强制填成 0；如果业务必须有值，应明确自己的补值规则。

### 4.3 数组下标和分段序号不是一回事

- `segments[0]` 是数组中的第一个分段，它通常有 `index: 1`。
- `segments[3]` 通常是 `index: 4` 的 `deal` 分段。
- `segments[3].data[0]` 才是第一条成交记录，`segments[3].data[1]` 是第二条成交记录。
- `index` 是协议分段编号，数组下标从 0 开始，不能混用。

## 5. `tick` 行情记录字段

在 `type` 为 `tick` 时，`data` 是按时间排列的行情状态数组。下面的字段是当前解析器已经确认并输出的字段。

| 字段 | JSON 类型 | 单位/格式 | 说明 |
|---|---|---|---|
| `seq` | 整数 | `0`–`255` | 记录头中的 1 字节序号标记，达到上限后可能回绕；不是全局唯一 ID。 |
| `time` | 整数 | `HHMMSS` | 例如 `91509` 表示 `09:15:09`，不是 Unix 时间戳。 |
| `price` | 数字 | 元 | 当前价。第一条记录若没有携带价格，可能为 `0`；后续会按稀疏规则继承已知价格。 |
| `open_price` | 数字，可选 | 元 | 开盘价。字段未出现或没有有效值时可能不返回。 |
| `prev_close` | 数字，可选 | 元 | 前收盘价。字段未出现或没有有效值时可能不返回。 |
| `high_pct` | 整数 | 百分比数值的 1/100 | 相对前收盘价的最高价变化。`-168` 表示 `-1.68%`。如果缺少计算所需字段，返回 `0`。 |
| `low_pct` | 整数 | 百分比数值的 1/100 | 相对前收盘价的最低价变化。`100` 表示 `+1.00%`。 |
| `change_pct` | 整数 | 百分比数值的 1/100 | 当前价相对前收盘价的变化。它不是直接存储的浮点百分比。 |
| `volume` | 整数 | 原始数量单位 | 累计成交量类字段。接口保留原始整数，不自动换算成“手”或“股”。 |
| `outer_vol` | 整数 | 原始数量单位 | 外部成交量类字段，保持原始整数。不要与 `volume` 直接混为同一口径。 |
| `amount` | 整数 | 原始金额类单位 | 成交金额类字段，保持原始整数；使用前应根据同一版本样本确认金额单位。 |
| `bid_avg_price` | 数字，可选 | 元 | 买方平均价类字段；仅在有有效值时返回。 |
| `bid_vol` | 整数 | 原始数量单位 | 买方数量类字段。 |
| `ask_avg_price` | 数字，可选 | 元 | 卖方平均价类字段；仅在有有效值时返回。 |
| `ask_vol` | 整数 | 原始数量单位 | 卖方数量类字段。 |
| `bid_levels` | 整数 | 原始档位数 | 买方盘口层级类字段。 |
| `ask_levels` | 整数 | 原始档位数 | 卖方盘口层级类字段。 |
| `capitalization` | 整数，可选 | 原始市值类单位 | 市值类原始值。当前接口不把它强行标注为总市值或流通市值，也不做单位换算。 |
| `bid_order_count` | 整数，可选 | 原始笔数 | 买方委托笔数类字段，按原始整数返回。 |
| `ask_order_count` | 整数，可选 | 原始笔数 | 卖方委托笔数类字段，按原始整数返回。 |
| `order_updates` | 数组 | 见下一节 | 当前记录对应的盘口挂单变化；通常为空数组，也可能包含多条变动。 |

### 5.1 为什么价格看起来是两位小数

协议中的价格按固定精度保存，接口已经转换为 JSON 数字。例如：

```text
协议原始值 1750 → 返回 price: 1.750000
```

因此用户程序应把 `price`、`open_price`、`prev_close` 等字段按元读取，不要再次除以 1000。数量和金额类字段则没有统一强制换算，保持返回的整数更安全。

### 5.2 百分比字段的正确换算

```text
实际百分比 = 返回值 / 100
```

例子：

| 返回值 | 实际显示 |
|---:|---:|
| `168` | `+1.68%` |
| `-168` | `-1.68%` |
| `0` | `0%`，也可能表示缺少计算所需字段 |

不要把 `-168` 直接显示成 `-168%`。

## 6. `order_updates` 盘口变动

`tick` 中的 `order_updates` 是数组。每一条变动包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `price` | 数字 | 发生变动的价位，单位为元。 |
| `status` | 整数 | 盘口变动类别代码。 |
| `status_desc` | 字符串 | 当前解析器提供的中文解释。 |
| `volume` | 整数，可选 | 变动数量。部分状态没有该字段。 |

当前代码中已确认的 `status` 对照如下：

| `status` | `status_desc` | 含义 |
|---:|---|---|
| `0` | `新增买` | 新增买方挂单。 |
| `1` | `新增卖` | 新增卖方挂单。 |
| `2` | `删除` | 删除已有盘口挂单。 |
| `3` | `撤销` | 撤销盘口挂单。 |
| `4` | `新增大单` | 新增大单类挂单。 |
| `5` | `更新大单` | 更新大单类挂单。 |
| 其他 | `未知` | 保留原始数字，不要当成已知类别。 |

`order_updates.status` 和 `deal.status` 是两个不同位置的状态字段，不能共用同一张代码表。`volume` 通常出现在状态 `0`、`1`、`4`、`5` 中；读取时仍应按字段是否存在判断，不要无条件索引。

## 7. `deal` 成交明细字段

在 `type` 为 `deal` 时，`data` 是成交记录数组。当前真实数据中，第一条和第二条可能类似：

```json
[
  {
    "seq": 0,
    "time": 91500,
    "price": 1.75,
    "volume": 96800,
    "status": 4
  },
  {
    "seq": 0,
    "time": 91509,
    "price": 1.76,
    "volume": 97000
  }
]
```

字段说明：

| 字段 | JSON 类型 | 单位/格式 | 说明 |
|---|---|---|---|
| `seq` | 整数 | 原始记录头标记 | 成交记录头中的 1 字节标记。已用多个日期、多个股票的真实数据核对，当前成交分段通常全部为 `0`；它不是逐笔成交序号，也不要把它当主键。 |
| `time` | 整数 | `HHMMSS` | 成交时间，例如 `91509` 表示 `09:15:09`。 |
| `price` | 数字，可选 | 元 | 成交价。该字段只在本条记录携带价格时出现。 |
| `volume` | 整数，可选 | 原始数量单位 | 成交量类原始整数。接口不自动换算单位。 |
| `seq_no` | 整数，可选 | 原始序号/标记 | 记录中携带的字段 3。只有原始记录包含它时才返回；它可能重复、不连续，不能单独作为全局唯一成交编号。 |
| `status` | 整数，可选 | 原始状态码 | 保留原始状态数字。当前没有足够稳定的公共语义映射，不要仅凭 `1`、`2`、`4` 等数字猜测买卖方向。 |

### 7.1 `seq` 全部为 0 是否正常

正常。`deal` 每条记录开头都有一个 1 字节标记，当前样本中这个标记对所有成交记录都是 `0`。它和 `tick` 中会在 `0`–`255` 之间回绕的 `seq` 不是同一种用途：

- `tick.seq`：记录头中的变化序号标记，常见于 `0`–`255` 循环；
- `deal.seq`：当前成交分段的记录头标记，实测通常固定为 `0`；
- `deal.seq_no`：记录内部可选字段，只有部分记录出现，而且不保证连续或唯一。

因此，读取成交明细时应使用数组顺序和 `time`，必要时再结合存在的 `seq_no`；不要等待 `deal.seq` 递增，也不要依据它丢弃记录。

### 7.2 `deal` 偏移问题说明

此前解析结果出现“`data[0]` 看起来正常、`data[1]` 开始错乱”，原因不是数组排序，而是字段宽度读取错误：

- `deal` 的价格、数量、序号、状态字段都按 4 字节读取；
- 旧解析逻辑把 `seq_no` 和 `status` 各读取成 1 字节；
- 第一条记录后读取位置少前进了 3 字节，下一条记录的头部就被从错误位置开始解释。

当前版本已统一按 4 字节读取 `deal` 的全部字段，并使用真实数据校验了完整成交数量、首条和第二条成交记录。用户程序不需要针对旧错位结果做补偿，也不要丢弃 `data[1]` 及后续记录。

### 7.3 不要强行给 `deal` 补列

推荐这样读取：

```python
for row in deal_rows:
    time = row["time"]
    price = row.get("price")
    volume = row.get("volume")
    status = row.get("status")
    # price/status 为 None 时，表示本条没有携带该字段
```

不要使用下面这种假设：

```python
# 不推荐：缺少字段不等于 0
price = row.get("price", 0)
status = row.get("status", 0)
```

如果需要导出 CSV，可以额外增加“是否存在”的标记，或者使用空字符串表示缺失，以免把缺失值误判为真实的 0。

## 8. 一个完整的处理示例

下面的代码展示如何找到 `tick` 和 `deal`，并安全读取可选字段：

```python
def find_segment(result, segment_type):
    for segment in result.get("segments", []):
        if segment.get("type") == segment_type:
            return segment.get("data", [])
    return []


ticks = find_segment(result, "tick")
deals = find_segment(result, "deal")

for tick in ticks:
    time_text = f"{tick['time']:06d}"
    change_percent = tick.get("change_pct", 0) / 100
    updates = tick.get("order_updates", [])
    print(time_text, tick.get("price"), change_percent, len(updates))

for deal in deals:
    time_text = f"{deal['time']:06d}"
    print(
        time_text,
        deal.get("price"),
        deal.get("volume"),
        deal.get("status"),
    )
```

注意：`segments` 也可以按 `index` 查找，但不要假设分段数组一定没有缺项；更稳妥的方式是同时检查 `index` 和 `type`。

## 9. HTTP 状态、业务错误和空数据

调用时应先判断 HTTP 状态，再解析 JSON。常见情况如下：

| 情况 | 可能表现 | 处理方式 |
|---|---|---|
| 服务未启动或端口不对 | 连接失败、连接被拒绝、超时 | 确认客户端已启动本地数据服务，并检查端口。 |
| 未登录或没有 D3 权限 | HTTP `403` | 回到客户端检查账号、权限和有效期。 |
| 路径写错 | HTTP `404` | 确认使用 `/d3/history`，不要自行改写路径。 |
| 返回包太短 | HTTP `200`，JSON 中有 `{"error":"data too short"}` | 检查日期、代码和服务日志；不要把错误对象当成正常数据。 |
| 返回长度不一致 | HTTP `200`，JSON 中有 `{"error":"length mismatch"}` | 记录请求参数并重试；如果持续出现，保留响应用于问题反馈。 |
| 日期没有可用记录 | HTTP `200`，但 `segments` 或其中的 `data` 为空 | 先确认是否为交易日，再换一个已知有数据的日期测试。 |
| 分段存在但只有 `raw_len` | `type` 为 `segment_2/3/5` | 这不是错误；当前这些分段只公开解压长度，不要按行情数组读取。 |
| HTTP `200` 但字段较少 | `deal` 某些行缺少 `price`、`status` 等 | 按稀疏记录规则处理，缺少字段不是自动补 0。 |

HTTP `200` 只表示本地服务返回了正文，不等于每个分段都有数据，也不等于每个业务字段都存在。

### 9.1 建议的程序判断顺序

```text
连接本地服务
  → 判断 HTTP 状态
  → 判断响应是否为 JSON
  → 判断顶层是否有 error
  → 检查 date / is_paid / segments
  → 按 type 处理 tick、deal 或 raw_len
  → 对每条记录按字段是否存在读取
```

## 10. 数据质量和使用边界

1. `time` 是日内 `HHMMSS` 整数，不是带日期的完整时间戳。程序入库时建议同时保存请求的 `date`。
2. `seq` 只有 1 字节，可能回绕，不能单独作为主键。需要去重时，应结合日期、股票、时间、数组位置以及实际存在的 `seq_no`。
3. 价格字段已经转成元；数量、金额、市值类字段保留原始整数。涉及统计、单位换算或跨数据源比较时，先用同一日期的样本验证口径。
4. `high_pct`、`low_pct`、`change_pct` 的单位是百分比数值的 1/100，不要再次乘 100。
5. 缺少字段和字段值为 0 是两种不同情况。对可选字段使用 `get`、存在性判断或数据库 NULL。
6. `deal.status` 当前只保证原始整数被正确解析，不应仅靠数字推断买方、卖方或主动性方向。
7. 交易日的开盘前、集合竞价、临时停牌等时段可能产生与连续交易时段不同的时间和字段组合，程序不要硬编码“每天第一条一定是 09:30:00”。

## 11. 版本修复记录

当前文档对应的 D3 解析规则包含以下修复：

- 修正 `deal` 字段读取宽度，避免从第二条记录开始发生字节偏移；
- 保留 `deal` 中实际出现的 `seq_no` 和 `status` 原始值；
- 输出 `tick.seq`，并让稀疏行情字段沿用前一条已知状态；
- 补充已确认的盘口摘要字段和委托笔数类字段；
- 对尚未展开的分段只返回 `raw_len`，不伪造字段定义；
- 对缺少前收盘价或当前价的记录，不计算出误导性的涨跌幅。

因此，升级后如果你的旧程序曾经针对错位结果写过特殊修正（例如跳过 `deal[1]`、手工向前补 3 字节或固定把状态截断为 0–255），应删除这些补偿逻辑。
